# 1.0.1: HTTP 567 下载失败

## 用户症状

普通视频已正确识别，1080P H.264 可选，下载时立即显示 HTTP 567。

## 证据

在用户报错的 B站普通视频页读取 DOM 中嵌入的 `window.__playinfo__` JSON，只记录主机名与流类型，不记录 Cookie、签名参数或完整资源 URL：视频首选 `upos-hz-mirrorakam.akamaized.net`，备用 `upos-sz-mirrorcosov.bilivideo.com`。

旧版 core.mjs 与 content.js 仅允许 bilivideo.com / bilivideo.cn，过滤掉首选可用节点。manifest 也未声明该节点。于是实际请求落到备用 CDN。该地址选择错误可稳定复现用户的 HTTP 567 症状。

近期相关上游报告（作为辅助线索，不代替本地验证）：https://github.com/yt-dlp/yt-dlp/issues/17847 。报告涉及相同节点与 567，另有 Range 头相关讨论。本次已确认的缺陷是地址过滤，没有在缺乏本机验证时增加请求头伪装或重试策略。

## 最小修复

仅增加 `upos-hz-mirrorakam.akamaized.net` 的 HTTPS 精确主机白名单与 host permission，保持播放器提供的地址顺序与签名参数原样。不允许通配的 akamaized.net、不更换主机、不生成新签名、不改变用户观看权限。版本提升为 1.0.1。

## 回归命令

```powershell
node --test tests/core.test.mjs tests/transfer.test.mjs
node tools/cdn-regression.mjs
node tools/browser-test.mjs
node tools/check.mjs
node tools/package.mjs
```

新增 CDN 回归使用实际 Edge 扩展 + 内容脚本 Port + 本地 WASM：相同播放响应内首选 Akamai 返回测试音视频、备用 bilivideo 返回 567。修复前断言失败，错误与用户相同；修复后生成完整 MP4，两个流均使用首选，不请求被拒的备用地址。

## 实网限制

用户页面已确认可正常播放并能读取内嵌播放信息。尝试重新加载并实测时，Computer Use 因无法可靠确认当前浏览器地址而停止。没有改用其他技术控制用户浏览器。最终真实视频下载尚未验证，交付时明确区分模拟 CDN 回归与真实站点成功。
